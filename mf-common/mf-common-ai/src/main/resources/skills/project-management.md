## 二、通用口径（所有场景都必须遵守）

1. **关联一律用主键 id**：需求用 `id`（UUID），版本用 `id`（UUID）。业务编号 `req_no` 只用于展示排序，**禁止作为关联键**（删除重建后会复用编号）；版本号 `code` 只是展示值。
2. **字典取值，禁止硬编码**：任务状态取 `pm_requirement_status`（待评审/开发中/待转测/测试中/验收中/已上线/已取消），评审结论取 `pm_review_result`（评审通过/补充修改/暂缓实施/未通过），优先级仅 高/中/低。"完成"= 状态进度 100（待转测/测试中/验收中/已上线）；"已转测"= post 阶段。
3. **版本筛选语义**（`requirement.queryAll` / `requirement.queryPageList*`）：
   - 不带 `iterationIds` 且不带 `includeUnassigned` → **全部版本汇总**，后端排除已归档（状态=已发布）版本的需求，但**包含"未纳入版本"的需求**；
   - 带 `iterationIds`（版本主键 id 数组）→ 精确命中这些版本；
   - 带 `includeUnassigned=true` → 叠加"未纳入版本"（无归属或指向已删除版本）的需求。
4. **日期**：一律使用系统提示词中的"当前日期"为基准（格式 yyyy-MM-dd），严禁使用训练数据里的日期。
5. **写操作后必须刷新**：新增/编辑/删除/批量操作完成后调用 `frontend.refresh`，触发前端按当前版本筛选重查主列表。
6. **工具名**：springdoc 会给部分工具名带 `_N` 后缀（如 `requirement.add_10`），以当前可用工具列表中的**实际名称**为准，按前缀识别即可。
7. **禁止传入的字段**（后端自动生成）：`id`、`reqNo`、`createBy`、`createTime`、`updateBy`、`updateTime`、`delFlag`、`month`（派生）、`hasPrdDoc`（派生）、`frontendDevIds` / `backendDevIds` / `qaTesterIds` / `ownerIds`（后端按姓名自动解析对齐）。
   **`tenantId` 尤其严禁传入**：后端新增需求时强制用当前登录会话租户覆盖，请求体里传的任何值都会被丢弃；误传 `1`(系统默认/超级租户)曾导致需求落到错误租户、当前租户下完全查不到。
8. **禁止占位符**：人员、提出人字段不得填"待分配""PMO""产品团队""不涉及"等值；未分配就传空串。

## 三、新建需求：必须自动补齐的默认信息 ★

### 3.1 必填字段（缺失必须追问，或能从描述合理推断时直接推断，禁止编造）

| 字段 | 说明 | 推断规则 |
|------|------|----------|
| module | 所属模块（后端强校验，为空直接报错） | 从描述提取系统/模块名，如"网关""控制台""大屏""数字员工""竞赛"；实在提取不到才追问 |
| featureDescription | 功能点描述（后端强校验，为空直接报错） | 用用户原话概括"要做什么"，禁止虚构不存在的功能 |
| level1Feature / level2Feature / level3Feature | 一/二/三级功能点 | 描述较长时按"模块—功能—子功能"拆分；一级允许为空 |

### 3.2 必须自动补齐的默认值（AI 主动填，不需要追问用户）

| 字段 | 默认值 | 规则与说明 |
|------|--------|------------|
| iterationId | ""（空串） | 默认"未纳入版本"。**必须显式传空串，不要省略该字段**：省略会落 NULL，在"全部版本"汇总里被 SQL 三值逻辑（NULL NOT IN 结果为 UNKNOWN）漏掉。若用户明确提到版本（如 v1.3.8、V1.3.9、本月版本），先按第六节查版本主键 id 再填；查不到就退回 "" 并在反馈里说明 |
| status | 待评审 | 字典 pm_requirement_status 中带 phase=pre;default=product 标记的项。不要填"开发中""已上线"等其它状态，也不要留空让后端兜底 |
| devProgress | 0 | 与"待评审"字典的 progress=0 一致 |
| priority | 高 | 仅允许 高 / 中 / 低。**默认=高**：用户未明确提及优先级时一律按「高」填（与后端兜底一致）；说"低优/有空再做"→低；说"紧急/高优/核心"也→高 |
| requestDate | **可不传**，后端自动填当天 | 若要显式传，用系统提示词"当前日期" yyyy-MM-dd，严禁使用训练数据里的日期 |
| requester | **可不传**，后端自动填当前登录用户姓名 | 若要显式传，必须是真实姓名；禁止占位符 |
| frontendDev / backendDev / qaTester / owner | ""（空串） | 默认未分配，禁止占位符。用户明确指定人员才填姓名，多人用英文逗号分隔 |
| reviewResult / reviewNotes / reviewDate | 不传（留空） | 评审结论属于评审流程产物，创建阶段不要臆断 |
| vendors / remarks / prdSection / highFidelityUrl / changeDate / changeContent / preMeetingQuestions / testPhase / testNodeId / testNodeName / testNodeDate / prdDocContent | 不传（留空） | 创建阶段无值；prdDocContent 是大文本，禁止传以免浪费 token |
| workload / frontendWorkload / backendWorkload | 不传 | 后端按人员自动计算：该侧无有效人员→0；有人员→默认 1 人天/人；总工时 = 各侧工时 × 该侧人数。用户明确给了工时才按需传 |
| devStartDate / devEndDate | 不传 | 后端按排期日历与工时自动推导 devEndDate；**严禁 AI 自己算日期填进去**。用户明确指定开始日期才传 devStartDate |

### 3.3 执行步骤（串行，每次只调用一个工具，等待返回后再调下一个）

1. **解析并补齐**：抽取 module、featureDescription、各级功能点，按 3.2 补齐默认值，形成 PmRequirement 请求体。仅当 module 或 featureDescription 完全无法推断时才追问，其余字段一律不追问。
2. **（仅当用户明确提到版本时）查版本主键**：`iteration.queryPageList*` 按 keyword 模糊匹配，取返回项 `id` 填入 iterationId；查不到 → 保持 "" 并说明"未匹配到版本，已按未纳入版本创建"。
3. **创建**：`requirement.add*`（POST /project/requirement），body 为 3.1/3.2 确定的字段，不含第二节第 7 条的禁止字段；从返回取 `data.reqNo`。
4. **刷新**：`frontend.refresh`，description 填"需求已创建，正在刷新列表..."。
5. **反馈**：需求编号 #reqNo、归属版本（版本名或"未纳入版本"）、本次自动补齐了哪些默认信息；若 iterationId 为空，提示可在版本筛选中勾选"未纳入版本"查看。

### 3.4 请求体示例（用户说"控制台加一个智能体 A2A 协议支持的需求"）

{ "module": "控制台", "level1Feature": "智能体", "featureDescription": "支持智能体 A2A 协议", "iterationId": "", "status": "待评审", "devProgress": 0, "priority": "高", "frontendDev": "", "backendDev": "", "qaTester": "", "owner": "" }

`requestDate` / `requester` 后端自动补齐（当天 + 当前登录用户姓名），`tenantId` / `reqNo` / `id` 等一律不传；示例里省略它们是推荐做法，可少占 token 且不会出错。

## 四、查询需求

- **列表**：优先 `requirement.queryPageList*`（分页，支持 iterationIds / status / priority / keyword / 人员）；甘特图联动用 `requirement.queryAll`（有 MAX_ALL_ROWS 安全上限）。
- **详情**：`requirement.queryById*`；**PRD 文档**：`requirement.getDoc`（单条）/ `requirement.queryDocBatch`（批量）。
- **回收站**：`requirement.listDeleted`；恢复 `requirement.restore*`；彻底删除 `requirement.deletePermanently`（不可恢复，需用户明确确认）。
- **回答进度/数量类问题优先走第八节汇总接口**，不要拉全量列表自行统计（返回数据量大，易触发模型 token 限额）。
- 查询时把版本筛选语义（第二节第 3 条）说清楚，避免把"全部版本"误解成"本月新增"。

## 六、版本/迭代管理

- 列表 `iteration.queryList*`（含 testNodes 转测节点与 spannedMonths），分页 `iteration.queryPageList*`，详情 `iteration.queryById*`（支持 id 或版本号）。
- 新建 `iteration.add*` / 编辑 `iteration.edit*` / 删除 `iteration.delete*`。
- 转测节点：`iteration.addTestNode`（传 iterationId + 节点名称/日期）、`iteration.deleteTestNode`。
- 归档 `iteration.archive` / 取消归档 `iteration.unarchive`。**归档后该版本需求不再出现在"全部版本"汇总中**（第二节第 3 条），需要查时须按版本精确筛选或先取消归档。
- 新建需求若用户提到版本，用本节查询得到的主键 id，不要把版本号字符串直接塞进 iterationId。

## 七、排期

- 查排期明细：`devSchedule.listBySelection`（一行 = 需求×人员×岗位，含起止日/工时/顺序/钉住状态，按 iterationIds + includeUnassigned 筛选）。
- 自动排期：`requirement.autoSchedule`（按容量装箱模型智能编排，可减少来回交互）；拖拽调期 `devSchedule.adjust`（与本人其他任务重叠时拒绝，调期后自动钉住）；钉住/取消 `devSchedule.togglePin`。
- 排期日历规则：`scheduleConfig.getConfig`（节假日/封版冻结日/补班工作日）、`scheduleConfig.updateConfig`。
- **禁止 AI 自行计算 devStartDate / devEndDate / workload 后写入**，一律交给后端按日历规则推导。

## 八、汇总分析（优先于拉明细自行统计）

- **月度进度**：`analytics.projectProgress`（GET /analytics/project-progress?month=yyyy-MM）。口径 = 管理周期 [startDate,endDate] 与本月有交集、或已开始且未设结束日期（进行中/规划中）的版本下的需求；返回状态分布、各版本完成率、总工时、本月交付数、逾期数。
- **本周周报数据**：`analytics.weeklyReport`（GET /analytics/weekly-report）。口径与月度进度对齐：**仅纳入管理周期覆盖本周一~下周日、或已开始且未设结束日期的活跃版本**下的需求（历史已发布/过期版本、无版本归属需求一律不纳入，避免全表混入）。返回字段：
  - `weekStart`/`weekEnd`：本周一~周日。
  - `iterations`：各版本进度（含 `code` 版本号、`name`、`status`、`completionRate` 完成率、`startDate`/`endDate` 版本管理周期），以及**两类数据（归纳素材 / 结构判定）用途不同、严禁混用**：
    - **★ 归纳素材（正文内容来源）**：
      - `weekFeatures[].featurePath` = 本周排期需求的 `一级>二级>三级` 功能路径；`weekFeatures[].description` = 该功能描述摘要 → 用于「本周主要工作」；
      - `scopeDescriptions` = 版本全部需求按主题分组、再按功能路径聚合的 `"主题｜一级>二级>三级：功能描述摘要；…"`（最多 6 主题 × 每主题 2 条）→ 用于「主要包括」，**同时提供功能层级结构与实际内容**。
    - **结构判定（不得写进正文）**：`weekCompletedFeatures` / `weekOngoingFeatures` = 只来自 `pm_dev_schedule` 表中排期落在本周(周一~周日)的需求功能点**短名**，两者都为空 = 该版本本周无排期任务；`scopeThemes` = 该版本全部需求按主题聚合的**短名**（供主题命名参考，最多 12 个）。
    - `weekFeatures[].progress` / `transferredToTest` 与 `weekWorkload`：本周排期明细状态与工时合计，仅作辅助与排序。
  - `activeRequirements`：进度<100 的进行中需求明细（辅助，不得用来写"本周主要完成"）。
  - `nextWeekPlan`：下周计划要点（按版本推导的短句，如"开展v1.3.8相关需求开发工作"），**仅供辅助，不要用它自行拼接正文**。
  - `nextWeekPlanText`：后端按「研发方面，一是……；二是……；三是……。」拼好的**下周工作正文成品**，逐字照抄。

### 8.1 周报生成逻辑（★ 格式以本节模板为唯一规范，严禁编造）

> **★ 本节是周报的唯一事实源**：前端不携带任何格式提示词。用户无论是点快捷按钮、手打一句
> "帮我输出本周周报"，还是用"生成周报""写本周工作总结"等任意措辞，都**必须完整输出
> 「本周工作：」与「下周工作：」两个段落**，不得因提问简短而省略格式、省略任一段落、
> 简化归纳、或改用自己的一套写法。

调用 `analytics.weeklyReport` 后，严格按下方**唯一格式规范**生成，**所有内容必须来自返回数据，不得臆造功能点或进度**。

#### ⚠️ 最高优先级规则
1. **本周工作的编号项 = 版本，不是需求**：直接遍历 `iterations`，有几个版本就写几条，编号一律用汉字「一是」「二是」「三是」……（**斜杠 `/` 不是编号，严禁拿它当条目分隔符**），**绝不允许把每条功能点写成独立编号项**，也**绝不允许只遍历有排期的版本而漏掉无排期版本**。
2. **★ 内容必须"归纳"，严禁拼功能点（本次优化重点）**：
   - 「本周主要工作」的唯一归纳素材 = `weekFeatures[].featurePath`（`一级>二级>三级` 功能路径）+ `weekFeatures[].description`（功能描述摘要）；
   - 「主要包括」的唯一归纳素材 = `scopeDescriptions`（**版本全部需求按主题分组、再按功能路径聚合的 `"主题｜一级>二级>三级：功能描述摘要；…"`**）；
   - **两处都要同时用「一二三级功能标题」判断能力归属 + 「功能描述」判断实际做了什么**，只拿标题拼名字或只抄描述都不合格；
   - **严禁把 `featureName` / `weekCompletedFeatures` / `weekOngoingFeatures` / `scopeThemes` 里的短名用顿号串起来交差**——旧版"本周主要工作智能体认证校验、智能体列表、导入按钮、MCP工具，主要包括控制台·开发中心"就是典型的功能点拼凑，属于本次必须消除的写法。
   - 这些短名清单**只用于结构判定**（该版本本周有无排期、是否转测、主题命名参考），**不得作为正文内容来源**。
3. **归纳方法（两处通用，必须执行）**：
   - 先看 `featurePath` / `scopeDescriptions` 里的**功能层级**：同一 `一级>二级` 下的多条属于同一能力域，先按层级归并，再读该条的描述确认具体做了什么；
   - 再按**能力/目标**合并同类项（例：`开发中心>我的智能体>认证校验` + `开发中心>我的智能体>智能体列表` + 各自描述里的"认证状态字段""源文件导入校验""结果回写" → 归纳为"智能体认证能力建设"）；
   - 用动宾短语写成自然语言，如「围绕……，完成……、支持……，并……」；
   - **功能标题只用于归并与命名方向，不得把标题原名串成名词清单**；
   - **只写描述里真实存在的能力**，不得引入描述之外的功能名、系统名、数字或进度；
   - 不得出现 `1.` `1.1` `（1）` 等条目编号、换行、斜杠 `/`、破折号占位；**严禁逐条抄录描述原文**；
   - 「本周主要工作」约 10–60 字，「主要包括」约 15–150 字；两者措辞不得雷同（前者=本周实际做了什么，后者=版本整体覆盖哪些方向）。
4. **数据缺失时的降级**：某版本 `weekFeatures[].description` 全为空 → 才允许退化用 `weekCompletedFeatures`/`weekOngoingFeatures` 的短名归纳（最多 6 个，且必须合并成一句话，不得纯罗列）；`scopeDescriptions` 为空 → 才允许用 `scopeThemes` 归纳方向。
5. 功能点短名（仅降级时使用）一律用后端返回的短名（已去除 `/` 占位段与 `--163定制` 噪声）。**禁止使用任何带 `模块/一级/二级/三级` 长路径、`///` 的字段**；若返回里仍出现单独的 `/`、`-`、`新增` 等占位词，直接丢弃该项。
6. 版本排序按 `weekWorkload`（本周涉及工时）降序，本周无排期的版本排到最后。

#### 本周工作模板（★ 唯一格式规范，严格照抄结构，不得改用"本周主要完成"或"本周主要推进"等其它句式）
```
本周工作：
研发方面，一是开展[版本号A]相关需求开发工作，本周主要工作[本周工作归纳]，当前进度[xx]%[（已转测）]，主要包括[版本方向归纳]；二是开展[版本号B]相关需求开发工作，本周主要工作[本周工作归纳]，当前进度[xx]%，主要包括[版本方向归纳]；三是……。
下周工作：
研发方面，一是……；二是……。
```
- **每个迭代版本或重点需求作为一条，编号依次为「一是」「二是」「三是」……**，一条之内必须齐备 4 要素：**版本号 + 本周工作归纳 + 是否转测 + 当前进度百分比**，用分号「；」分隔各条，最后一条用句号收尾；**条目之间严禁出现斜杠 `/`**。
- `[版本号]`：取 `code`（无 code 用 `name`），**小写 v 保持原样**（如 v1.3.8、se1.0.0、v2026.11），只写一次。
- `本周主要工作[本周工作归纳]`：**★ 基于 `weekFeatures[].featurePath`（一级>二级>三级）+ `description`（功能描述）做语义归纳**，写成一句连贯的自然语言，说明本周实际完成了哪些能力/改造。按「归纳方法」先按功能层级归并、再用动宾短语组织，例如
  `开发中心>我的智能体>智能体列表：列表新增认证状态字段及筛选…` + `开发中心>我的智能体>认证校验：弹窗需导入源文件与认证材料…`
  → `围绕智能体认证能力建设，完成认证状态展示与筛选、认证校验弹窗及源文件导入校验，并补充认证结果回写与导出能力`；
  **严禁把 `featureName` 短名用顿号串成清单**（如「智能体认证校验、智能体列表、导入按钮、MCP工具」是错误写法）。**统一用"本周主要工作"这一措辞**，不拆成"本周主要完成…并推进…"两句，不给单条功能点单独标进度；描述信息不足时才按最高优先级规则第 4 条降级。
- `当前进度[xx]%`：取 `completionRate`（×100 取整，如 0.98→98%），**是版本整体进度，不是单条功能点进度**，所有条目都必须写。
- `[（已转测）]`：**仅当该版本 `transferredToTest > 0` 或 `weekCompletedFeatures` 非空时**，紧接在进度后追加「（已转测）」，如 `当前进度99%（已转测）`；**未转测/未完成的版本不写这个标注，只写"当前进度[xx]%"**（这就是"已转测的标注已转测、未完成的标注当前进度"）。
- `主要包括[版本方向归纳]`：**★ 基于 `scopeDescriptions` 归纳出版本整体覆盖的方向/主题**。其中每条格式是 `主题｜一级>二级>三级：功能描述摘要；一级>二级>三级：功能描述摘要…`，**必须同时用「一二三级功能标题」定位能力域 + 「功能描述」提炼实际内容**，两层结合后写成方向，而不是把主题名去掉 `·` 罗列：
  - 先按功能标题把相近条目归并，再从描述里抽取"建了什么能力"，例如
    `控制台·运维监控｜运维监控>全链路监控：调用日志增加失败原因、请求参数与响应内容…；运维监控>Skills明细：安装量改为总安装下载量…` + `控制台·数据看板｜数据看板>汇总表：总部展示15分钟维度真实数据…`
    → `主要包括运维监控的调用链路日志追溯与失败原因展示、Skills 安装下载量口径治理及数据看板实时指标展示等方向`；
  - **严禁把 `主题｜` 后面的功能路径原名抄成清单**（如「全链路监控、Skills明细、汇总表」），标题只用于判断归属；
  - `scopeThemes` 只作为主题命名参考，**不得直接抄成「控制台开发中心、运营管控、运维监控」这类名词串**；主题较多时归并成「……等方向」；
  - 与「本周主要工作」措辞不得雷同（前者讲本周实际动作，后者讲版本整体范围）；
  - `scopeDescriptions` 与 `scopeThemes` 都为空（版本下无需求）→ 整句省略，只写版本、进度。

#### ⚠️ 版本周期覆盖本周、但本周无排期任务 → 也要显示
- `iterations` 已包含"管理周期覆盖本周"的所有版本（含 `weekCompletedFeatures`/`weekOngoingFeatures` 均为空的版本）。**这些版本必须仍作为一条编号项出现**。
- 唯一允许的省略：两组都为空时**不写「本周主要工作…，」这一段**（没有本周排期可报，不得编造），写法：`一是开展[版本号X]相关需求开发工作，当前进度[xx]%，主要包括[scopeThemes 归纳]；`。
- **严禁**因为某版本本周没排期就把它从本周工作里整条删掉（这正是之前 se1.0.0 丢失的原因），也**严禁**用 `activeRequirements` 冒充本周工作。

#### 数据来源与映射
- **唯一权威版本集合 = `iterations`**（每个版本固定生成一条编号项）；「本周主要工作」只取 `weekFeatures[].featurePath + description` 归纳，「主要包括」只取 `scopeDescriptions`（主题 + 一二三级功能路径 + 功能描述）归纳，**无需再跨数组关联**。
- `weekCompletedFeatures` / `weekOngoingFeatures` / `scopeThemes` 仅用于结构判定（有无本周排期、是否转测、主题命名）与数据缺失时的降级，**不得**作为正文内容来源。
- `activeRequirements` 仅作辅助理解与排序，**不得**用来写"本周主要工作"或"主要包括"。

#### 下周工作（必须与本周工作一起输出，且只输出一次）
```
下周工作：
[逐字照抄 nextWeekPlanText]
```
- **`nextWeekPlanText` 是后端已按固定格式拼好的成品正文**，形如
  `研发方面，一是开展v1.3.9相关需求开发工作；二是开展v2026.11相关需求开发工作；三是开展se1.0.0相关需求开发工作。`
  **逐字照抄即可，严禁改写、严禁重新编号、严禁再拿 `nextWeekPlan` 数组自行拼接**。
- **严禁使用斜杠 `/` 作为条目分隔符**：每一条必须以汉字编号「一是」「二是」「三是」开头，条目间用分号「；」，结尾用句号。
  （旧提示词里写「按 `一是/二是…` 编号」，模型曾把斜杠当分隔符，输出成「一是开展A/开展B/开展C」，故改为后端给成品句。）
- **必须且只能输出一个"下周工作："段落**，与本周工作成对出现；**严禁重复输出两遍**，也严禁把每个版本拆成独立一行罗列。
- 若 `nextWeekPlanText` 为空，输出 `研发方面，暂无明确下周计划。`。

#### 篇幅与语气
- 版本项要体现"本周工作归纳 + 当前进度/是否转测 + 版本整体方向归纳"，**不要只写笼统的"开发中，进度30%"**，也不要退回"本周主要完成/推进"的旧句式，更不要退回功能点清单。
- 「本周主要工作」「主要包括」都是**归纳句**：用逗号/顿号组织动宾短语，写成连贯自然语言；**严禁把短名清单平铺成「A、B、C、D」当作归纳**（这是本次优化要消除的首要问题）。
- 版本项之间用分号「；」分隔，全文用句号收尾。
- **严禁出现返回数据之外的任何数字、功能点名称或进度**；**严禁输出单独的 `/`、`-` 等占位符**。

## 九、前端联动

- 打开页面：`frontend.navigate`（target 为路由/视图）；其它 DOM 交互：`frontend.click` / `frontend.fill` / `frontend.openModal`。
- 刷新列表：`frontend.refresh`（派发全局 ai-refresh 事件，前端按当前版本筛选重查主列表），已声明为延迟下发，在文本反馈之后执行。
- 写操作（三/五/六/七 节的增删改）完成后都要调用；纯查询不需要。

## 十、禁止行为

- ❌ 不得仅返回本指南内容而不调用任何工具
- ❌ 不得省略新建需求的 iterationId（省略 = NULL，会导致"全部版本"汇总查不到）
- ❌ 不得在请求体里传 tenantId（后端强制用当前会话租户覆盖，传了只会误导）
- ❌ 不得编造 module / featureDescription / 人员姓名 / 版本 id / 汇总数据
- ❌ 不得用占位符填充人员字段或提出人
- ❌ 不得自己计算并填入 devEndDate、workload、各类 *Ids
- ❌ 不得传入 id / reqNo / tenantId 等后端自动生成的字段
- ❌ 不得用 req_no 作为需求关联键
- ❌ 不得使用训练数据中的日期，必须使用系统提示词的"当前日期"
- ❌ 回答进度/统计类问题时不得拉全量需求列表自行聚合（改用第八节汇总接口）
- ❌ 不得一次性发起多个工具调用（必须串行：调用一个 → 等待返回 → 调用下一个）
